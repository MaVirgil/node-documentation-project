What is a REST API

A REST API is a stateless web-based API used to store, fetch and manipulate data, usually - but not necessarily - in connection with the CRUD functionality of an application. Many publically available REST APIs exist to serve data from some large dataset. Examples include The Movie Database and Open Weather.

Public APIs like these usually only expose GET routes, but it is also very common to expose the backend functionality of an application through a closed API, enabling the full range HTTP-based CRUD functionality. These proprietary services will usually protect the majority of routes through authorization and authentication, only exposing basic functionlity like registering and logging in/out on unprotected routes

Designing endpoints

Say we were to design a small API enabling CRUD-operations on a smaller dataset of some kind, in this example we will use movies. We will not be worrying about the actual implementation of the code, but instead focus on the design of the routes - that is, which HTTP-method used on which endpoint results in what behaviour.

A REST API design works by defining a specific action with a verb + a noun. The verb comes from the HTTP-method of the the request, and the noun is specified in the URL (the resource locator). This means that when designing endpoints, one should avoid using verbs at all, instead an endpoint should define some resource. In our movie example the first obvious endpoint might therefore be https://ourmovieapi.com/movies. Now if a client wants to retrieve a list of all movies in our system, they can make a request to our endpoint using the GET method. Conversely if they want to add a new movie to our database they can do a POST request to the same endpoint, defining the data in the body of the HTTP-request.

So what happens if a client has the ID of a specific movie, and wants to fetch all the data related to that movie? In this case we can define a path variable on our endpoint in order to target a single resource in our dataset. Now, the client can make a GET request on the endpoint https://ourmovieapi.com/movies/{id} to fetch a single movie instead of having to fetch every resource at once. This endpoint can also be used to implement routes for HTTP-methods like PATCH or DELETE.

For a very simple REST API, these two endpoints are really all we need to implement basic CRUD functionality, and our finished API might look something like this:

HTTP-method Endpoint Function
GET ourmovieapi.com/movies Get all movies
GET ourmovieapi.com/movies/{id} Get specific movie by id
POST ourmovieapi.com/movies Add new movie
PUT ourmovieapi.com/movies/{id} Replace movie resource by id
PATCH ourmovieapi.com/movies/{id} Update movie resource by id
DELETE ourmovieapi.com/movies/{id} Delete a movie resource by id

There are of course, ways to make an API even more useful to the client: Right now they can either a) fetch every single movie in our dataset, or b) fetch a single movie, provided they know the id of the resource. Depending on the expected use of the API, we might consider implementing some sort of search functionality or filter, to provide a middle ground between these two ways of finding resources. A common way to achieve this is by using query parameters, which consist of key-value pairs defined when hitting and endpoint. One choice is to create a fully-fledged search functionality based on the title of the movie, and to then accept a query parameter on the GET-route like so: https://ourmovieapi.com/movies?q=<some-search-string>.

Considering that we probably have more data on a movie than just a title, we might instead decide to implement some basic filtering: We can take a few optional parameters like genre, rating and release-year. Now it is possible for a client to build a request that does a pretty good job at filtering down our big dataset. One might look at comedy movies from 2010 with the following GET-request: https://ourmovieapi.com/movies?genre=comedy&release-year=2010. Now the client can do the same for the year 2020, and do a comparative analysis on the average rating, the budget or the box office numbers.

Just by implementing basic filtering we have enabled our REST api to be used for a whole host of useful and creative application outside of the basic CRUD-operations defined originally.
