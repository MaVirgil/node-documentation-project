Representing dates

Date objects in JavaScript are - surprisingly - used to represent points in time. Under the hood a date object just describes a number of milliseconds before or after midnight UTC on January 1st 1970, a moment known as the "Unix epoch".

This method of representing time hasn't always been the standard. You've probably heard of the infamous Y2K bug, which was caused by computer systems - in order to save valuable memory - only using two digits to store years, which made it impossible to differentiate between the years 2000 and 1900. In the end, the Y2K bug was not as catastrophic as many people feared thanks to a lot of people working very hard to fix it, while cursing the lack of foresight that led to the problem to begin with.

If you're young like me, and sad that you weren't around for this terribly exciting time, I've got good news: Many systems today store Unix time in 32-bit integers, which will overflow in 2038, meaning that if you play your cards right, you might just get to work very hard to fix it, while cursing the lack of foresight that led to the problem to begin with.

Luckily, JavaScript uses 64-bit floats to store Unix time, so you'll never have to worry about your code suddenly breaking. Software developers 270,000 years down the road, of course, might curse your lack of foresight.

Handling timezones

While Unix time is always in UTC (Coordinated Universal Time), and describes a discrete, unambiguous point in time, when the value of a Date object is parsed in a browser, it is converted to the local timezone of the system the code is running on. If you just want to display a date on the client, it should probably be formatted for the client's timezone, but say you want to save the timestamp of some user action in a database. This should probably be stored in UTC instead, and any conversion to/from a region-specific timezone can be handled on the client-side.
